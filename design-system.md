# Magnertia ERP — Design System

Extracted from the Financial Management Dashboard mockup, cross-checked against the
already-implemented tokens in [`src/styles.css`](src/styles.css). Where the mockup and
the implementation disagreed (mockup uses violet, implementation uses navy blue +
beige), **the implementation wins** — it's the deliberate Magnertia brand palette and
is already live across ~20 routes. Don't reintroduce violet.

## Approach: CSS variables + Tailwind v4 `@theme inline`, not a `tailwind.config.js`

This repo is on Tailwind v4, which is CSS-first — there is no `tailwind.config.js`.
Design tokens live as CSS custom properties in `:root` (`src/styles.css`), and
`@theme inline` re-exposes them as Tailwind utilities (`bg-primary`, `text-success`,
`rounded-xl`, etc). This is already the established pattern; keep extending it there
rather than adding a parallel config file or a `tailwind.config.ts`. Benefits:

- One source of truth per token (change `--primary` once, every utility updates).
- Runtime-themeable (dark mode / white-labeling later is a class toggle, not a rebuild).
- No risk of two conflicting theme systems in the same repo.

### Chart palette (`--chart-1` … `--chart-5`)

Sequential blue tints used for donuts/bars, from strong to soft — this is what makes the
aging donuts and expense distribution read as "brand" rather than generic rainbow charts:
`#0A3C75` → `#336B9F` → `#729FC9` → `#B2C9DF` → `#E2D9C5` (beige, reserved for the
smallest/last slice, e.g. "Other Expenses" or "120+ Days").

`--chart-bar-expense: #E2D9C5` is a dedicated soft-beige token for the "Expenses" bar in
the Revenue vs. Expenses combo chart, so it doesn't compete visually with `--primary`
(Revenue bars) or the green net-profit line.

Status colors are semantic, not decorative — success/warning/destructive map 1:1 to
`StatusBadge` tones (`paid/online/active` → success, `pending/degraded` → warning,
`overdue/offline` → destructive). New status values should map into one of these three
buckets rather than inventing a new color.

## Typography scale

Font: **Inter** (`--font-sans`, `--font-display`), loaded via Google Fonts in
`__root.tsx`. No separate mono font is used for numbers — instead, `.tabular` (defined in
`@layer base`) applies `font-variant-numeric: tabular-nums` to Inter itself, which keeps
digits fixed-width in KPI values and table amounts without switching typefaces.

| Role                                                 | Size / weight                        | Class pattern                                                            |
| ---------------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------ |
| Page title (H1)                                      | 26–28px / bold, `tracking-tight`     | `font-display text-[26px] font-bold sm:text-[28px]`                      |
| Card title (H3)                                      | 15px / semibold                      | `font-display text-[15px] font-semibold`                                 |
| KPI value                                            | 22px / bold + `.tabular`             | `font-display text-[22px] font-bold tabular`                             |
| Body / table cell                                    | 12.5–13px                            | `text-[13px]` / `text-[12.5px]`                                          |
| Label / caption                                      | 12px medium                          | `text-[12px] font-medium`                                                |
| Micro / eyebrow (table headers, aging bucket labels) | 10–11px, uppercase, `tracking-wider` | `text-[10px] font-medium uppercase tracking-wider text-muted-foreground` |
| Numeric data (amounts, %, ratios)                    | inherits size + `.tabular`           | always pair currency/number spans with `tabular`                         |

Headings use `letter-spacing: -0.015em` globally (set once in `@layer base`, not per
component).

## Spacing & radius conventions

- **Radius**: single base token `--radius: 0.75rem` (12px), scaled via `--radius-sm`
  (−4px) through `--radius-2xl` (+8px). Cards use `--radius-xl`. Don't hardcode `rounded-*`
  pixel values on new surfaces — use the `card-soft` utility or the `rounded-{sm,md,lg,xl,2xl}`
  scale so a future radius change is one edit.
- **Card padding**: `p-5` (20px) is standard for dashboard panels; `p-4` for mobile
  cards/compact rows.
- **Grid gaps**: `gap-4` (16px) between cards in a row; `mt-5` (20px) between rows of
  cards.
- **Shadows**: two tokens only — `--shadow-card` (resting) and `--shadow-elevated`
  (hover). Applied via the `card-soft` utility class and `hover:shadow-[var(--shadow-elevated)]`.

## Reusable component patterns

These are the patterns visible repeated across the mockup and already implemented as
either shared components (`src/components/erp/`) or established JSX patterns inline in
route files. New dashboard-style modules should reuse these rather than inventing new
card shapes.

### 1. KPI card — two competing conventions, pick by mockup fidelity

There are **two** KPI card components in this repo and they are not interchangeable:

- **Convention A — icon-left** ([`components/erp/StatCard.tsx`](src/components/erp/StatCard.tsx)):
  40–48px circular icon on the left with a tinted background (`bg-{color}/10`), label
  above a bold `.tabular` value, and one of three caption treatments: a colored+arrow
  `delta` line (`StatDeltaLine`, for vs.-previous-period comparisons), a plain gray
  `neutralText` caption (`captionTone="muted"`, the default — for period labels like
  "This Year"), or a **colored, arrow-less** `neutralText` caption (`captionTone="positive"
| "negative"` — for a figure that carries meaning on its own, like Accounts Payable's
  "24.18% of Total" in red on the Overdue Amount card). Used by Dashboard, Transactions,
  General Ledger, and Accounts Payable — all pages built from a real pixel mockup.
- **Convention B — icon-top-right** ([`components/erp/KpiCard.tsx`](src/components/erp/KpiCard.tsx)):
  icon in the top-right corner, uppercase tracking-wide label, optional pill-style delta
  badge, optional `hint` text. Used by the 9 earlier scaffolded pages (Payables,
  Receivables, Ledger, Expenses, Assets, Vendors, Stations, Users, Revenue) that predate
  any pixel mockup for this project.

**Rule: when a module has a real mockup, use Convention A (`StatCard`).** Convention B
is legacy scaffolding, not a competing design decision — don't propagate it to new
mockup-driven modules. The 9 existing Convention-B pages haven't been migrated (out of
scope until they get their own mockups), so both will coexist for a while; that's
expected, not a bug.

### 2. Donut chart panel (Expense Distribution)

Card with `CardHeader` (title + info icon + filter dropdown), centered donut
(`recharts` `PieChart`/`Pie`, `innerRadius`/`outerRadius` for the ring, `paddingAngle={1}`,
`stroke="none"`), a total value + caption absolutely centered inside the donut hole, and
a vertical legend list below with color dot + label + right-aligned value.

### 3. Bar + line combo chart (Revenue vs. Expenses Trend) / dual-line variant

`ComposedChart` with two `Bar` series (primary + `--chart-bar-expense`) and one `Line`
series (`--success` green) for net profit, custom legend row above the chart (not
recharts' built-in legend), `CartesianGrid` horizontal-only, axis lines/ticks hidden,
currency-compact Y-axis formatter (`$0M`–`$5M`).

Accounts Receivable's Receivables Trend uses the same construction with **no bars** —
just a plain `LineChart` with two `Line` series (`--primary` for Total Receivables,
`--success` for Collected Amount) — because both series are running totals, not a
paired actual-vs-actual comparison the way Revenue/Expenses bars are. Same legend/grid/
axis treatment either way; drop the bars when both series are trend lines rather than
period totals.

### 4. Aging summary (donut + table)

Two-column layout: donut on the left (same construction as pattern 2, smaller,
140×140) with centered total, and a compact table on the right (`Aging Buckets | Amount
| % of Total`) whose rows share the same color dots and ordering as the donut slices.
Always paired with an "As of Today" filter and an info-icon tooltip trigger in the
header.

**Aging-bucket color is page-scoped, not a fixed universal palette.** The Dashboard's
AR/AP aging donuts use the monochrome blue-shades chart palette
(`#0A3C75→#336B9F→#729FC9→#B2C9DF→#E2D9C5`). Accounts Payable's own Aging Summary donut
uses a semantic green→blue→orange→red→gray gradient
(`#22C55E→#3B82F6→#F59E0B→#EF4444→#9CA3AF`) for the identical 0-30/.../120+ Days bucket
structure — deliberately, because color signals risk on a liabilities-focused page. Both
are correct for their own page; don't force one palette everywhere. When building a new
aging-bucket chart, check its own mockup's colors rather than copying whichever aging
donut you saw most recently.

### 5. Transaction list row

Table (desktop) / card (mobile, via `DataTable`'s `mobileCard` prop) pattern: `Date |
Reference | Description | Amount`, reference rendered as a link-styled button, amount
signed and colored (green positive, red negative in parens), divider rows via
`divide-y divide-border`.

### 6. Master-detail list + filter toolbar (Transactions)

A `card-soft` panel containing: a toolbar row (search input with left icon, one or more
`FilterSelect`s, decorative `FilterButton`s for anything not yet wired to real filtering,
"Clear All"/"Save View" text links), a table with a leading checkbox column and a
trailing per-row `⋮` `DropdownMenu` (actions), and a pagination footer (`Showing X to Y
of N entries` + page-size `FilterSelect` + numbered page buttons). Selecting a row
optionally reveals a second `card-soft` panel beside the table (`xl:grid-cols-[1fr_380px]`)
with a `Tabs` header and a close (`X`) button — used for the Transaction Details panel.
Reuse this whole shape for any future list module (Payables, Receivables, Ledger) rather
than rebuilding search/filter/paginate/select-to-view-detail from scratch — it's not
DataTable (which is read-only, no selection/checkboxes/pagination), it's a heavier
pattern for pages that need real interaction.

### 7. Hierarchical tree table (Chart of Accounts)

Expandable parent/child rows in a single `<table>` — chevron + indentation in one
"expand column" (first column), font-weight stepping down by depth (`font-bold` root →
`font-semibold` mid-level → regular leaf), rest of the columns render normally at every
depth. Shared component: [`components/erp/TreeTable.tsx`](src/components/erp/TreeTable.tsx).
Deliberately **not** built on the Radix `Collapsible` primitive — `CollapsibleContent`
wraps its children in a `div`, which can't legally sit between `<tr>` siblings in a
`<table>`, so expand/collapse state is just a local `Set<string>` of collapsed ids
instead. Reuse this for any future hierarchy view (Cost Centers, Consolidation entities)
rather than hand-rolling indentation math again.

### 8. Page-level view-switching tabs vs. panel-level detail tabs

Two different `Tabs` visual treatments exist, both using the same shadcn `Tabs`
primitive, styled differently by intent:

- **Page-level tabs** (General Ledger's Chart of Accounts / Account Activity / Trial
  Balance): underlined text tabs — `TabsList` with `bg-transparent p-0 gap-6`, each
  `TabsTrigger` with `border-b-2 border-transparent` that becomes `border-primary
text-primary` when active, no pill background. Switches the entire main content view.
- **Panel-level tabs** (Transactions' Details/History/Attachments/Notes inside the
  detail panel): the shadcn default pill style (`bg-muted` track, active tab gets
  `bg-background` + shadow). Scopes to a sub-section of a fixed-size panel.

Pick by scope, not by habit: page-level content switch → underlined; tabs living inside
one card/panel → default pill style.

### 9. Dialog-based detail/create/action views (Accounts Payable)

Transactions' master-detail pattern (#6) puts row detail in an inline `card-soft` panel
occupying the table's sibling grid column. That only works when the sidebar column is
free. Accounts Payable's sidebar is fully committed to four persistent summary cards
(Aging Summary, Top Vendors, Payment Summary, Quick Actions), so there's no room for an
inline detail panel — row selection instead opens a shadcn `Dialog` (Invoice Details,
with a Vendor Information sub-section, Record Payment / Approve action buttons in the
footer). The same `Dialog` primitive backs the New Invoice creation form and the Record
Payment form. **Choose inline panel vs. dialog based on whether the sidebar column is
already spoken for** — don't default to one or the other out of habit.

### 10. Quick Actions grid — sidebar card vs. full-width footer bar

An icon-in-circle + label button grid, currently page-local (`payables.tsx`,
`receivables.tsx` — promote to `components/erp/` if a third module wants the same
shape, per this repo's "promote on second use" rule). Each action opens the relevant
`Dialog` or navigates; actions with no defined backend flow (e.g. "Vendor List") are
inert toasts, same as Transactions' "+ New Transaction" stub — see architecture.md's
stub-vs-build rule.

Two layouts exist depending on how many actions there are: Accounts Payable's 4 actions
fit as a `grid-cols-4` card **inside** the right sidebar stack, alongside Aging
Summary/Top Vendors/Payment Summary. Accounts Receivable has 6 actions, which don't fit
a sidebar card at a readable size — its mockup instead runs Quick Actions as its own
full-width `card-soft` **below** the table+sidebar grid (`grid-cols-3 sm:grid-cols-6`).
Pick the layout the actual action count (and the mockup) calls for, not whichever you
built last.

### Shared primitives

- `card-soft` (utility class in `styles.css`): the single card container used everywhere
  — white bg, `--border`, `--radius-xl`, `--shadow-card`.
- `CardHeader` ([`components/erp/CardHeader.tsx`](src/components/erp/CardHeader.tsx)):
  title + info icon + right-aligned filter/action slot. Promoted out of `routes/index.tsx`
  once a second module needed it.
- `FilterButton` / `FilterSelect` ([`components/erp/FilterButton.tsx`](src/components/erp/FilterButton.tsx)):
  `FilterButton` is a decorative pill trigger (`label + ChevronDown`, no built-in state)
  for controls not wired to real logic yet (e.g. Dashboard's "Monthly"/"YTD" chart
  toggles). `FilterSelect` is its functional counterpart, backed by a real `<select>`
  with the same visual shell — use this one whenever the filter actually needs to do
  something (Transactions' Type/Status/page-size controls).
- `StatusBadge`: pill with colored dot, tone resolved from a status-string lookup table.
  Four semantic tones — covers `paid/posted/online/active` (success), `pending/degraded/
approved/due soon` (warning), `inactive/canceled/credit memo` (muted), `overdue/offline`
  (destructive), plus a 5th **info** tone (blue, `#3B82F6`) added for Accounts
  Receivable's `partially paid` — an in-progress/neutral-informational state that isn't
  resolved (success) but isn't a warning either. Extend this table when a new module
  introduces a status that's clearly one of these five buckets; don't fork a page-local
  copy, and don't force a status into the wrong bucket just to avoid adding a 6th tone —
  add one if a status genuinely doesn't fit (as info didn't).
- `TypeBadge` ([`components/erp/TypeBadge.tsx`](src/components/erp/TypeBadge.tsx)): for
  **categorical** tags that aren't good/bad (e.g. transaction type: Invoice/Payment/Bill/
  Receipt/Journal Entry) — distinct from `StatusBadge`, which is semantic. Each category
  gets a fixed color from existing tokens (`primary`, `success`, `chart-2`, `warning`,
  `chart-5`); don't reuse `StatusBadge`'s tone system for non-status categories.
- `AppShell`'s `Topbar` accepts an optional `topbarActions` slot (rendered between "All
  Companies" and the refresh button) for page-specific primary actions like Transactions'
  "+ New Transaction" button. Pass `topbarActions` to `AppShell`, not a custom topbar.
- `PaginationFooter` ([`components/erp/PaginationFooter.tsx`](src/components/erp/PaginationFooter.tsx)):
  "Showing X to Y of Z {entityLabel}" + page-size `FilterSelect` + numbered page buttons.
  Promoted out of `transactions.tsx` once General Ledger needed the identical control for
  its Chart of Accounts table. `total` must always be the real count of what's being
  paginated, never a fixed headline number (see architecture.md's "Mock pagination" note).
